# 备份与打包：保存这个头像可还原的完整集合

读这份文件的时机：用户要求**备份 / 归档 / 导出 unitypackage / 迁移工程**，或问「怎么才能完整还原」。

> 目标：按用户需要保存可还原的范围，**并说明不在备份内的内容**。
> **依赖分析是起点，还要补上未被依赖图追踪的输入与可重建环境。** 精简头像备份与整个工程的完整快照是**不同交付物**；用户要完整工程时，不要擅自缩成依赖子集。

## 0. 先量后设计

动手前先量三个数，并确认目标是**头像迁移**还是**原工程还原**：

| 量什么 | 怎么量 | 记录 |
| --- | --- | --- |
| 整个 `Assets/` | 递归统计文件与字节数 | `<TOTAL_ASSETS_SIZE>` |
| 头像自身目录 | 递归统计，**含 `.meta`** | `<AVATAR_SIZE>` |
| **头像的外部依赖** | `AssetDatabase.GetDependencies()`，再补人工确认的输入（见 §1） | `<DEPENDENCY_SIZE> / <TOP_LEVEL_COUNT> / <FILE_COUNT>` |

某个外部目录可能很大，而头像只用其中少量文件。精简备份可按清单**逐文件拷贝**；若那目录本身就是用户要的完整源集合，整目录备份也合理。**记录保留与排除的理由，不以体积小证明完整。**

## 1. 依赖分析：范围从哪来

```csharp
using System.Linq;
using UnityEditor;

// 以头像目录下全部资产为初始根，保留未被当前 prefab 引用的预设。
var roots = AssetDatabase.FindAssets("", new[] { "<AVATAR_FOLDER>" })
    .Select(AssetDatabase.GUIDToAssetPath)
    .Where(p => !AssetDatabase.IsValidFolder(p)).Distinct().ToArray();
// 将已确认的目录外源场景 / prefab / 配置路径并入 roots，再取传递依赖。
var deps = AssetDatabase.GetDependencies(roots, true);
```

- 分出**外部资产依赖**：`Assets/` 开头、但**不在头像目录边界内**的路径；目录判断要含 `/` 边界，避免把同前缀目录误算进来。
- 按顶层目录统计文件数与体积。**文件与其 `.meta` 一起备份**；保留相关目录的 `.meta`，以免丢失目录 GUID。
- 把「头像自身 + 外部依赖 + 人工补充输入」的**去重清单落盘**，例如 `_deps_filelist.txt`。镜像还应包含选定源目录中**未被 AssetDatabase 索引、但还原所需**的原始文件。
- ⚠️ **`GetDependencies` 只返回 Unity 已知的依赖**，不保证涵盖：任意字符串路径加载、动态选择的 `Resources` 资产、外部配置、编辑器生成器输入、自定义导入逻辑。**这些入口要逐项检查并补入清单**（见 §3.3）。
- **分开记录「稳定源资产」与「预览/构建生成物」。** 要能从保存的源配置与包版本重建，**不能只备份一次 Play 克隆或临时控制器**。

## 2. 备份集长什么样

```text
<BACKUP_ROOT>/<NAME>_<TIMESTAMP>/
├── <NAME>_Avatar.unitypackage      ← 需要导入包时附带；完整性取决于内容
├── Mirror/Assets/<AVATAR_FOLDER>/  ← 源文件与 .meta，保持原路径
├── Mirror/Assets/<EXTERNAL>/       ← 清单中选定的外部依赖
├── Mirror/ProjectSettings/         ← 原工程还原所需设置，含 Unity 版本信息
├── Packages-manifest/              ← 工程实际存在的 UPM / VPM 清单与锁文件
├── PackageBodies/                  ← 必须保留的包体 / 本地依赖（见 §2.1）
├── PACKAGES.md                     ← 包 ID、版本、来源与还原方法
├── _deps_filelist.txt              ← 精确文件清单
├── README.md                       ← 范围、还原步骤与未验证项
└── MANIFEST.sha256                 ← 最终文件校验；不包含自身
```

以上是**目录示意，不是固定私有路径**。估算源文件、包体、导出包及临时文件的总占用；**不要套用其它工程的体积或节省率**。

⚠️ **纯文件镜像保存的是磁盘内容**——未保存的场景/资产状态**不会**自动进入备份。

### 2.1 包（`Packages/`）：清单之外何时必须保存包体

UPM 的 `packages-lock.json`、`manifest.json` 与 VPM 的 `vpm-manifest.json` 提供**互补**信息；保存实际存在的文件，**不假设每个工程都有三份**。来源不只有 registry 与 embedded，还可能有 **Git、本地目录/压缩包和内置包**。

| 来源 | 怎么处理 |
| --- | --- |
| **registry / Git** | 记录**精确版本或提交**、registry/仓库来源、必要的还原说明。**不能假设某版本永远可下载**；需离线还原、来源不可用或有本地修改时，保存可用副本。 |
| **embedded** | 包体位于 `Packages/<PACKAGE_ID>/`。VPM 安装的包也可能显示为 embedded；此字段**既不证明不能重装，也不证明只记 ID 就能重装**。保留本地修改、自制包、以及无法确认可重新取得的包体。 |
| **local / tarball** | `file:` 引用可能在工程之外。**备份真实内容**，记录迁移后的路径安排，**不能只保留原机器绝对路径**。 |
| **built-in** | 记录匹配的 **Unity 版本**；它们通常由编辑器提供。 |

`PACKAGES.md` 至少列出：**包 ID、版本/提交、来源、是否有本地修改、是否保存包体、还原方式**。

⚠️ **embedded 包会优先于同名 registry 包被使用**，还原时要核对**实际生效**的版本。

**只排除已确认可重建的缓存/临时包**（例如某些 VRCFury 版本的 `com.vrcfury.temp`）；**不要按目录名猜测并丢掉必需内容**。

对外发布备份或导出包前，**检查第三方资产与包的再分发许可**；私人可还原备份**不等于**可直接放到公开仓库的发布物。

## 3. unitypackage：单根目录与完整依赖是两项要求

### 3.1 导出范围与路径

- `AssetDatabase.ExportPackage` **保留资产的工程路径**；它**不提供**导出时自动重排路径的参数。确需重排时，在**隔离副本**中处理，并验证引用与路径加载。
- **不加 `IncludeDependencies`**：只导出选定资产；选目录时用 `Recurse` 包含子目录。**外部依赖需另行提供。**
- **加 `IncludeDependencies`**：Unity 会扩展依赖范围，**可能带入意料外的脚本/资产**，并保留它们原来的路径。包内资产如何处理取决于 Unity/工具版本——**不能宣称此标志总会把全部 `Packages/` 脚本导出**，也**不能**用它代替包环境备份。

```csharp
AssetDatabase.ExportPackage(
    new[] { "<AVATAR_FOLDER>" }, "<OUTPUT_PATH>.unitypackage",
    ExportPackageOptions.Recurse);
```

该示例只保证**所选范围的导出方式**，**不保证包单独可还原**。用户要自包含包时，需把**可分发的完整资产依赖**纳入导出清单；**包依赖与工程设置仍要另列**。单根结构用**实际归档内容**验证。

### 3.2 外部依赖放哪

放进 `Mirror/Assets/`，**按原路径**保存资产和 `.meta`。这样保留 GUID，并兼容原有字符串路径加载。还原仍要检查**缺失文件、GUID 冲突、版本兼容性**——**不能承诺「零风险」**。

Unity 序列化资产引用通常靠 **GUID/fileID**，带着原 `.meta` 正确移动资产**不必然**破坏这些引用；但**硬编码路径、部分工具配置、层级动画路径**要分别检查。

**只导入头像目录的 unitypackage 后，还必须补齐外部依赖。**

### 3.3 移动或裁剪依赖前检查路径加载

先搜完整路径，再搜相对片段、加载调用与配置：

```bash
rg -n -F 'Assets/<FOLDER_TO_MOVE>' Assets Packages ProjectSettings
```

同时检查项目脚本、CI、外部配置与工具约定。**一次文本搜索没有结果不代表没有动态依赖。**

⚠️ `Resources.Load` 使用**相对 `Resources` 的路径**——把资源移出该目录或改其相对路径都会失效。

发现实际路径依赖时，**优先保持原路径**；用户已授权重组时，可在副本中同时修正路径使用者并验证。**不要在源工程里为凑单根临时来回移动资产。**

### 3.4 导出耗时与「假失败」

导出耗时受资产数量、压缩、磁盘与编辑器状态影响，**MCP 可能超时**。**超时不表示导出失败或已经停止**——先查任务状态、日志和输出，再决定是否重试（见 [07-04-verification-discipline.md](../07-验证与排查/07-04-verification-discipline.md)）。**避免并行重试写同一文件。**

⚠️ **文件大小连续不变只能说明暂时没有可见增长，不能证明导出完成。** 优先取得导出调用**正常返回/完成标记**，再验证归档**可完整读取**、路径清单符合预期，并计算校验值。没有完成证据时标记为未确认。

## 4. 打包前检查

- [ ] 确认已有用户范围：**备份、导出、测试导入、本地构建、上传是不同操作**；按已授权范围执行，**不为同一已授权操作重复请示**。
- [ ] 记录磁盘源状态与未保存改动；需要保存时，**只保存本次范围内已授权的源改动**，避免把预览值写成默认值。
- [ ] Unity 导出时处于**稳定的 Edit 状态**，没有编译/导入/另一导出同时改动输入。文件镜像也应使用**一致的源快照**。
- [ ] 源资产、配置或包发生变化后**更新清单**；固定的「24 小时」期限**不能**判断清单是否仍有效。
- [ ] 使用**唯一**目标目录与导出路径，避免覆盖旧备份；磁盘余量要含镜像、包体、归档和临时写入空间。
- [ ] 备份脚本**只读源文件**；清单、日志与校验写到**备份位置**。

## 5. 校验

1. **对照清单核验镜像**：逐文件检查是否存在、**字节数与哈希**是否匹配源快照。**文件数相同不足以证明内容相同。** 包含文件/目录 `.meta` 与人工补充输入。
2. **最终校验清单**：所有导出与说明文件写完后生成 `MANIFEST.sha256`，**排除该清单自身**。若沿用旧 `MANIFEST.md5`，同样排除自身；MD5 可发现一般误拷贝，但**不用于证明不受恶意篡改**。之后改了备份内容就**重建清单**。
3. **检查 unitypackage 内容**：它通常是 **gzip 的 tar**，资产条目使用 **GUID 目录**与 `pathname`/`asset.meta`，普通文件另有 `asset`；**文件夹条目不一定有 `asset`**。可只读检查，无需解压到工程：

   ```python
   import tarfile
   from collections import Counter
   from pathlib import PurePosixPath

   with tarfile.open("<PACKAGE_PATH>.unitypackage", "r:gz") as archive:
       paths = []
       for member in archive:
           if member.isfile() and member.name.rsplit("/", 1)[-1] == "pathname":
               data = archive.extractfile(member).read()
               paths.append(data.decode("utf-8").rstrip("\x00\r\n"))
   print("pathname count:", len(paths))
   print(Counter("/".join(PurePosixPath(p).parts[:2]) for p in paths))
   ```

   核对**每个完整路径**及预期资产清单；前缀统计只是辅助，**不能代替完整性检查**。
4. **核对包环境**：将 `PACKAGES.md` 与 UPM/VPM 清单、锁文件、保存的包体逐项对照。它们的直接/传递依赖范围不同，**条目数不必等于** `vpm-manifest.json` 的 `dependencies` 数量。

## 6. 还原顺序（写进 README）

1. 先**校验备份本身**，再在**新建或隔离工程**里按记录选择 Unity 版本。原工程还原需要对应 `ProjectSettings`；**迁移到现有工程时不要盲目覆盖该工程设置**。
2. 按记录恢复包清单与必要包体；用适当的 UPM/VPM 工具解析可下载依赖，**修正本地路径**并核对**实际版本**。**单纯复制三个 JSON 不等于包已经恢复。**
3. 选择完整 `Mirror/Assets/` 还原，**或**导入 unitypackage 并补齐它未包含的外部文件。**保留原路径与 `.meta`**；不要把还原操作变成对现有无关资产的无审查覆盖。
4. 让 Unity 完成导入与编译，检查**缺失脚本、材质、引用和菜单源配置**。在既有授权范围内重建并验证；**源文件一致不证明构建或客户端行为一致**。
5. 记录**实际执行过的**恢复演练与未验证项。未做隔离工程还原时，**只能称「文件/归档校验通过」**，不能声称完整还原已验证。

## 7. 常见坑

- 依赖图**不是**所有动态输入的清单；unitypackage **也不是**整个 Unity 工程快照。
- embedded/本地包**只记名字**可能丢失唯一副本；包来源与可下载性**要核实**。
- **超时**或**文件大小稳定**都不能单独证明导出成功。
- **GUID 引用与字符串路径依赖是两套机制**，移动影响应分别验证。
- PowerShell 变量名**不区分大小写**，避免用仅大小写不同的名字保存源/目标路径。含非 ASCII 的脚本若需兼容 Windows PowerShell 5.1，**UTF-8 with BOM** 可避免错误解码；PowerShell 7 不普遍要求 BOM。

## 8. 与「上传前快照」的关系

[06-01-sdk-upload-and-versioning.md](06-01-sdk-upload-and-versioning.md) 第 9 节的「上传前可回退点」是**本分册的轻量版**：

- 上传前的**最小要求**：能回到「上传前那一版」。工程层（git 提交或目录副本）+ 资产层（本次改动的工作 prefab/场景/菜单/参数）+ 记录层（`Logs/` 报告）。
- 用户要**完整可还原归档**或**迁移到另一台机器**时，走本分册的完整流程（依赖清单 + 包体 + 校验 + 还原 README）。
- **没有可回退点就不要开始上传流程**，尤其当本次改动含不可逆操作（重命名对象、改骨骼、动材质）时。
